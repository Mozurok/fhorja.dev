# evals/

Manual eval harness for the my_work_tasks workflow. Each scenario under [`scenarios/`](./scenarios/) describes an input prompt, the expected response shape, and pass criteria you can verify by reading the model's output. Designed to be run by hand in any AI tool the workflow targets (Cursor, Claude Code, Copilot, Codex, Gemini CLI, etc.) so the same eval surface works regardless of which tool is consuming the workflow.

## Why this exists

Fhorja is a **contract**: every command's output is supposed to follow a fixed shape (frontmatter, mandatory sections, a `### Handoff` block with `Run now:` body, etc.). When that contract drifts (because a model regresses, a command file changes, or a shared block goes out of sync), tasks downstream break in ways that are slow to diagnose.

This eval harness catches drift before users hit it. It is not exhaustive coverage; it is a **regression net** of representative cases that exercise the load-bearing properties of the workflow.

## What is in scope

The <!-- count:scenarios -->144<!-- /count --> scenarios cover the whole corpus, from the five starters through every wave since. The table below is the roster; it is generated-adjacent in the sense that `check_corpus_indexed` fails when a scenario file has no row here, so the two cannot drift. There is deliberately no prose enumeration of which wave contributed which numbers: the one that used to sit here stopped at scenario 101 while the corpus reached 117, and a list nothing checks only decays. Each row's Validates cell names the ADR or decision the scenario locks, which is the same information at the only granularity worth maintaining.

## Cadence

Inspired by the Anthropic guidance ("read 10-20 transcripts weekly; multi-turn evals are critical; 20-50 cases to start"):

- **Weekly (light)**: pick 1-2 scenarios, run them, read the response against the criteria. ~10 minutes. The goal is to keep contact with how the workflow performs in practice.
- **Per release (full)**: run all <!-- count:scenarios -->144<!-- /count --> scenarios before tagging a release. Failures block the release until the relevant command file is fixed (or the criteria are revised after a deliberate decision and an ADR).
- **After spec or shared-block changes**: run scenarios 01 and 03 (the most contract-sensitive ones) to confirm the change did not regress the output shape.

## How to run

Each scenario file follows the same template (see [`scenarios/template.md`](./scenarios/template.md)):

1. **Setup**: pre-existing artifacts or environment the scenario assumes (clean repo, fixture task folder, synthetic git diff, etc.). Most setups require nothing more than a fresh chat session against a checkout of this repo.
2. **Input prompt**: the exact text to paste into your AI tool. Variables like `<client>__<project>` are intentional placeholders; substitute with throwaway values.
3. **Expected response shape**: structural rules the response must satisfy (must-have sections, fence patterns, frontmatter, etc.).
4. **Pass criteria**: numbered checks you verify by reading the response. A scenario passes when every numbered check passes.
5. **Failure modes to watch**: common ways the response can pass-but-be-wrong (e.g., schema-correct but fabricated content). These are the high-value attention points.
6. **Notes**: related ADRs, related commands, known issues, history of past failures.

For a guided walkthrough that prints each scenario in turn (so you can paste from the terminal into your AI tool), run:

```bash
./evals/scripts/run-evals.sh
```

The script prints each scenario file to stdout and waits for you to press enter before continuing. It does not call any model API; the manual loop is intentional.

## The automatable subset (runs in CI)

Most scenarios are behavioral: they check a model's output against numbered criteria, which needs a human reading the response. A subset, though, depends on a **static property of this repo**, and those parts run in CI on every push via [`evals/scripts/structural-evals.py`](./scripts/structural-evals.py).

The harness does not run a model. It asserts the repo invariants a subset of scenarios depend on, so if one breaks, the corresponding scenario cannot pass. It runs every check registered in that script's `CHECKS` list. Each is labelled with the scenario it enforces, or, when the invariant predates or postdates any scenario, with the ADR that locked it. The script prints the full roster and the pass count on every run, so read it there rather than from a list here: the hand-maintained roster that used to sit in this section fell nine checks behind the registry.

This is a subset by design, and the harness prints exactly that: the behavioral scenarios stay manual, and no claim of full automated coverage is made. Run it locally with:

```bash
python3 ./evals/scripts/structural-evals.py
```

## What to do when a scenario fails

A failure usually means one of three things:

1. **The command file regressed**. Recent edits to `commands/<name>.md` changed the output shape. Fix: edit the command file to restore the contract, or update the scenario's pass criteria if the change was deliberate (and capture the rationale in CHANGELOG and possibly a new ADR).
2. **A shared block drifted**. The canonical block in `commands/_shared/<name>.md` changed but did not propagate to all consumers. Fix: run `./scripts/sync-shared-blocks.sh` and confirm `./scripts/lint-commands.sh` is clean.
3. **The model itself regressed**. Less common, but real (model lineup churn, sampling variance). Fix: capture the failing transcript, re-run with the most recent stable model in your tool, decide whether the regression is reproducible. If it is, file an issue.

The `### Notes` section at the bottom of each scenario file is where past failures and their resolutions are recorded. Keep adding to it; the history is a learning surface for future maintainers.

## Adding new scenarios

1. Copy [`scenarios/template.md`](./scenarios/template.md) to `scenarios/NN-short-title.md` (next free number).
2. Fill in Goal, Setup, Input prompt, Expected response shape, Pass criteria, Failure modes, Notes.
3. Add a row to the table above.
4. Open a PR. Include rationale in the description: what gap in coverage does this fill?

The corpus already passed Anthropic's starting guidance of 20-50 cases (<!-- count:scenarios -->144<!-- /count --> scenarios); past that point, what to add matters more than how many. Prioritize scenarios that exercise:

- **Routing edges**: cases where two commands could reasonably be the next step; the scenario validates that the right one is chosen.
- **Multi-turn flows**: the workflow's value is in sequences (`task-init` to `impact-analysis` to `decision-interview` to `implementation-plan`); single-turn scenarios miss most of the contract.
- **Adversarial inputs**: malformed, ambiguous, or context-poor prompts that the workflow should handle gracefully (often by asking a targeted question rather than guessing).

Each scenario should be **deterministic enough that two reviewers agree on whether it passed**. If the pass criterion requires judgment ("the response is clear"), refine it ("the response includes a `Reason:` line of at least 10 characters that names the specific phase").

## Running the spine set against a model

The harness has two halves and they do different jobs.

`evals/scripts/run-evals.sh` is the manual walk over the whole corpus. It prints a scenario, you paste the prompt into your AI tool, you read the output against the pass criteria. It calls no model API and it never will: a human reading the output is the point of that half.

`evals/scripts/run-spine-evals.py` runs the few scenarios listed in `evals/spine-evals.json` against a model you name, and leaves the prompts, the responses, the rubric and a verdict under `evals/runs/<run-id>/`. That directory is gitignored: the durable record is a line in the scenario's `## History`, not megabytes of model output in git.

The manifest elects <!-- count:spine-scenarios -->10<!-- /count --> scenarios and records in the file why each one earned a slot. Adding another is a decision, so write the reason in the same field.

```
# print every prompt and rubric, invoke nothing. Works on a dirty tree.
python3 evals/scripts/run-spine-evals.py --dry-run

# run them against any command that reads a prompt on stdin.
# Precondition: a clean working tree. Check it first, because the run refuses otherwise.
git status --porcelain
python3 evals/scripts/run-spine-evals.py --model-cmd '<your command>' --model-label '<what you ran>'
```

`--model-cmd` is a shell command, so the runner knows no vendor and names none. It runs from the repository root, so a prompt saying `Run @commands/x.md` can open the file, and that same reach is why a graded run has a precondition: **the working tree must be clean**. Two reasons, and the weaker one is the obvious one. A dirty tree makes a write by a scenario indistinguishable from one that was already there. The stronger one is that a model graded against a state no commit describes produced a verdict nobody can reproduce later. `--dry-run` invokes nothing and writes nothing, so it is exempt.

Setting `FHORJA_EVAL_ALLOW_DIRTY_TREE=1` starts anyway. It exists so this runner's own test suite can exercise the plumbing while someone is editing the runner, and it is an environment variable rather than a flag on purpose: a flag is what gets reached for to make a refusal go away. A run that uses it says so on stdout and states that the run is not reproducible. It buys convenience and pays with the evidence.

**Your `--model-cmd` decides what the grader can see, and most rubrics need the whole run.** A CLI in
plain print mode returns its FINAL message. When a scenario's chain runs several commands inside one
invocation, every intermediate command output is gone, and the grader can only answer the criteria
that survive in the summary. Measured 2026-09-01 on scenario 137: the run was correct end to end,
it created the local commit, and five of seven criteria came back UNCERTAIN with notes saying "the
response is a single late-run turn" and "compliance on every other command turn cannot be verified".
Two of seven PASS on a run that did everything right is a harness reading, not a workflow reading.

The fix belongs in your command string, not in the runner: the runner knows no vendor and this is
vendor knowledge. Flatten a streaming transcript to text before it reaches stdout. For Claude Code:

```
--model-cmd 'p=$(cat); claude -p --output-format stream-json --verbose "$p" 2>/dev/null \
  | jq -r '"'"'select(.type=="assistant") | .message.content[]? | select(.type=="text") | .text'"'"''
```

**Isolate the run from the machine it runs on.** A CLI loads the operator's own setup, and on
2026-09-22 three parts of it reached the verdicts. Installed skills shadowed the clone's
`commands/*.md`: `~/.claude/skills` was 68 bodies behind the repository, and a run loaded the stale
`approve-plan`. Global MCP servers put an authorization note after the Handoff, which failed "ends
with the Handoff" in two scenarios. User settings changed the response language. For Claude Code, add
`--setting-sources project,local --disable-slash-commands --strict-mcp-config --mcp-config
'{"mcpServers":{}}'`, and include each tool call in the flattened stream (a `tool_use` block's
`input.command`), so a criterion about order, such as a display before a commit, has something to read.

Measured on a three-step prompt: the flattened form returns all three intermediate messages, plain
print mode returns only the last. Other CLIs differ; `kimi` has `--output-format stream-json` too.
Whatever you use, check once that a multi-step prompt comes back with its middle in it.

`--grader-cmd` defaults to the same command. `--grade-without-setup` runs a scenario whose setup mode is `shell` anyway; the runner has never executed a scenario's shell setup and does not start, so what the flag removes is the skip, and the scenario is then graded against a tree its setup never prepared.

A manifest entry with `"setup": "fixture"` names a checked-in script under `evals/fixtures/spine/` instead. The runner creates an empty temp directory, runs `bash <script> build <dir>` and nothing else, and replaces `{fixture}` in the prompts with that path. After every turn it records which files the turn added, changed or removed under the directory, plus the script's own `probe` output, in `disk-after-turn-N.txt`, and hands the same text to the grader as ground truth. That last part exists because a grader that reads only the response passed scenario 137 on a claimed ledger write no file showed (ADR-0217). `"turns": "independent"` sends each turn as its own conversation with a fresh fixture: scenario 08 compares two runs that must not see each other, and scenario 125's second turn needs something still staged. Scenarios 03, 08, 125, 137, 141, 142, 143, 144 and 145 use a fixture, and all of them but 03, 137 and 145 use independent turns; 01 attaches a probe. The fixtures of 137 and 145 give the chain a throwaway product repository and report whether the workflow checkout's branch or HEAD moved; 145's remote is a local bare repository with no pull request host, so the push is read from it and the draft PR step is graded as an environment limit. Until 2026-09-24 both ran in the workflow repository, whose remote is real. The fixtures of 142 and 143 also watch REPO_ROOT itself: the build records its `projects/*/active/*/` listing and HEAD, and the probe reports the folders added since and whether HEAD moved. The tree comparison above cannot see either, because `projects/` is gitignored and a commit leaves the tree clean; `scripts/tests/test-spine-repo-root-watch.sh` proves the probe against a temporary repository standing in for REPO_ROOT.

Refusals have their own exit codes and none of them invents a verdict: exit 2 when there is nothing to run (no `--model-cmd`, no `FHORJA_EVAL_MODEL_CMD` and no `--dry-run`), on `--record` without `--model-label`, or on a `--scenario` that matches no manifest entry, exit 3 on a rubric under three criteria, exit 4 when a model command fails or writes nothing OR when a scenario wrote into the working tree, and exit 5 on a dirty tree at the start of a graded run. Git that cannot answer is exit 5 as well, because a tree state nobody could read is not a clean one. After each scenario the tree is compared against the state before it and anything new is an ERROR with the paths named, never a verdict: an eval reads this repository, it does not edit it. The overall verdict is computed by the runner, never read from the grader's reply, and a criterion the grader did not answer counts as UNCERTAIN.

One pass per scenario. No retry, no cost accounting, no loop.

`--record` appends exactly one line to the scenario's `## History`, and that line is the durable record:

```
- 2026-08-30: run 20260830T060449Z-4b342a | model=<label> grader=<label> | UNCERTAIN 0/3 | failed: none | artifacts: evals/runs/20260830T060449Z-4b342a/90/
```

Everything under `evals/runs/` is disposable and gitignored. The History line is what survives, so a later check can read back which model was run, when, and how it scored.

`--record` needs `--model-label`: the runner cannot tell which model sits behind a shell command, and a verdict with no model attribution is not worth recording. It appends and never rewrites, and a scenario that ended in ERROR or was SKIPPED gets no line at all, so a run that broke on infrastructure cannot poison the history.

## What this harness does **not** do

- The manual walk calls no model API. `evals/scripts/run-evals.sh` prints a scenario and waits; you copy the input prompt into whichever AI tool you are using. The spine runner above is the one half that does invoke a command, and only for the <!-- count:spine-scenarios -->10<!-- /count --> scenarios the manifest elects.
- It does not measure cost, latency, or token usage. For that, see [`scripts/measure-tokens.py`](../scripts/measure-tokens.py) and the `scripts/baseline-*.md` snapshots.
- It does not enforce that pass rates exceed a threshold; the harness is a regression net, not a benchmark suite. Failures are signals, not numbers to optimize.
- It does not decide anything on your behalf. A verdict from the spine runner is evidence to read, not a gate: UNCERTAIN defers to a human, and no threshold anywhere turns a score into a decision.

The automated half now exists for the spine set and lives alongside the manual one, consuming the same scenario files rather than a copy of them. The manual layer remains the source of truth for what each scenario means.
